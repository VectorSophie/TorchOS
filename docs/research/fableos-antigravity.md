# Prior Art Research — FableOS and Google Antigravity OS Demo
Researched 2026-08-23 for TorchOS v2 (Claude Code–style "system mechanic" assistant over a constrained privileged broker, `torchd`).

---

## FableOS (`robiot/fable-os`)

- **Purpose**: Experimental x86_64 OS whose kernel is controlled directly by an LLM (Claude) through a natural-language-first interface — "no shell, no commands, no `ls` and no `cat`." Built by a single developer (robiot / Elliot Lindberg). Explicitly a research/demo artifact, not a daily-driver OS.
- **Base / architecture**: From-scratch x86_64 kernel — Multiboot/GRUB boot, its own heap/VFS/ramfs/FAT32, its own network stack (lwIP + mbedTLS compiled into `kernel.bin`), its own framebuffer/window-manager/font stack, and its own subset C compiler that the model uses to write and run native programs on the fly. A "Driver VM" — a bounded instruction set over hardware primitives (MMIO/DMA/bus-mastering) — is the substrate the model uses to author device drivers live. ~72k LOC of custom C/asm plus ~53k LOC of tests (+330k LOC of vendored lwIP/mbedTLS). Runs only in QEMU; **the project states it has never booted on physical hardware.**
- **Agent model**: A single LLM (Claude) drives a tool-call loop against 64 exposed kernel "syscalls," up to 16 tool-rounds per request. It can write native C programs and launch them as GUI apps, persist named "capabilities" to a FAT32-backed registry, and register bounded autonomous "agenda" tasks that run at boot or on a schedule without a human present.
- **Privilege model**: Essentially none — the single most important cautionary datapoint. Quoting the project's own docs: *"One CPU, ring 0, cooperatively scheduled, no userspace, no memory protection, no IOMMU, no privilege separation. Every tool call runs in the kernel's own address space... All pages are mapped read-write-EXECUTE."* The model has a `mem_write` tool for direct arbitrary kernel-memory writes. The C compiler bounds *compiled* programs somewhat (loop-fuel counter, stack-bounds check, constant-only call targets, no function pointers/floats/goto) but explicitly: *"nothing bounds a pointer"* once code is running. The Driver VM sandboxes register access via an allowlist but **not DMA**: *"the VM bounds what the PROGRAM touches and nothing bounds what the HARDWARE does."* TLS runs with `MBEDTLS_SSL_VERIFY_NONE` unless built with an extra flag. The Anthropic API key lives only in RAM but is reachable by the model's own `mem_read` tool. The one integrity control that *is* real: a structurally-enforced separation between model prose and kernel-emitted trace lines (`[bracket]` lines can only originate from `tool_dispatch()`) — "an audit trail enforced structurally rather than promised." The docs are explicit about the limit: *"nothing here stops the model from lying in prose. It stops the model from lying in the kernel's voice."*
- **Recovery model**: `fault_guard_run()` (setjmp/longjmp) catches faults from most tool-invoked code paths, enabling "diagnose without dying." A self-repair mode (`-DFABLEOS_REPAIR_DEMO`) lets the model patch the running kernel's `.text` live, constrained to: address in-bounds, an `expect` field matching current live bytes, identical byte count, original bytes saved first (revertible). The docs flag the limit themselves: *"Nothing claims the new bytes are CORRECT — only well-formed, in-bounds, boundary-exact and reversible."* Reversibility is not correctness. Compiled/JIT'd code runs on a stack the fault guard doesn't watch — a bad pointer there halts the machine with no recovery. No filesystem/system-level snapshot concept — only this single in-place, single-edit revert.
- **Compatibility strategy**: One target: QEMU/x86_64. Driver model ships only bring-up basics (serial, PCI enumeration, e1000 NIC, PS/2 mouse, RTC, ACPI, ATA); the model is expected to write anything else live. A demonstration of "LLM writes a driver for hardware it's never seen," not a real hardware-compatibility strategy.
- **UI model**: Pure natural-language chat, no shell, no discrete commands. Model prose interleaves with structurally-protected `[bracket]` trace lines.
- **What works well**: The prose-vs-trace structural separation is a real, reusable idea. The "model authors a driver for unseen hardware" workflow is a legitimate capability demonstration. The bounded compiler is a reasonable minimal sandbox for the compiled-code layer. Fault-guard-with-single-edit-revert is a clean minimal "try/catch/undo one change" primitive.
- **What breaks / limits / fails to generalize**: Zero isolation is the entire point of the project — ring-0, all-RWX, no IOMMU means a DMA-capable driver the model just wrote can corrupt anything. TLS-off-by-default plus a plaintext-in-RAM API key readable by the model's own tools is a credential-exposure design flaw. Never run on physical hardware — none of TorchOS's real concerns (firmware, ACPI, an actual Intel iGPU) are addressed. Self-repair patches are provably reversible but never provably correct. No broker, no policy layer, no human-approval step, no dry-run — strictly "model decides → kernel executes."
- **What TorchOS should reuse conceptually**: The structurally-unforgeable trace/audit-log separation. The bounded-autonomy "agenda" pattern for unattended scheduled actions (consecutive-failure retirement, per-item run caps, boot-only ephemeral items, durable disable-on-crash, refusal to let an unattended action end the machine's power state, wrapping every unattended run in a fault guard). The named/persisted "capability" registry idea — gated by policy, not freely writable by the model to storage it also controls.
- **What TorchOS must explicitly avoid**: Any ring-0/root-equivalent execution path for the assistant model. DMA-capable or IOMMU-less hardware access authored by the assistant. Insecure-by-default network trust. Secrets reachable from the assistant's own execution/tool context. Treating "the change can be reverted" as equivalent to "the change was validated before being applied." Letting the model be the sole judge of whether its own action is safe.
- **Confidence / verifiability note**: **High confidence.** All claims come directly from the project's own repository documentation (`README.md`, `README.os.md`, `AGENTS.md`) — an unusually candid self-assessment, including its own worst-case admissions, from a small, openly experimental, single-maintainer project. One caveat: an unrelated web-search coincidence, "Claude Fable 5" (a separate Anthropic model/product name), is **not** this project and was not used in this analysis.

## Google Antigravity / "Gemini OS" build-an-OS demo

- **Purpose**: A reported flagship capability demo for Google's **Antigravity** agent-first development platform (real product; Antigravity 1.0 announced 2025-11-18 alongside Gemini 3; Antigravity 2.0 shown at Google I/O 2026), claiming its multi-agent "teamwork" mode used Gemini 3.5 Flash to autonomously build a small working OS from a single prompt.
- **Base / architecture** (of the *workflow*, not an OS-internals reference): **Sentinel** (front-desk manager, structures intent, supervises completion) → **Orchestrator** (decomposes into milestones/dependencies) → **Explorer** agents (formal strategy docs, no code) → **Worker** agents (implement, run tests) → **Reviewer** agents (independently check design correctness) → **Critic** agents (adversarial stress-testing) → **Auditor** agents (independently verify "authenticity and robustness," including static-analysis aimed at catching hardcoded outputs/mock facades/cheating). Reported scale: 93 sub-agents, 15,314 model calls, ~339M input tokens (~2.6B total incl. cache/output/thinking), ~12 hours wall-clock, ~$916.92 API cost. Reported result ran FreeDoom; Google's own post admits it lacks floating-point math, hardware acceleration, complex multithreading.
- **Agent model**: Explicitly hierarchical and role-specialized — builder (Worker), design grader (Reviewer), adversarial tester (Critic), cheating/fakery detector (Auditor) reported as four distinct roles, not one agent self-certifying its output.
- **Privilege model**: **Not documented anywhere found.** No detail on what sandbox/VM isolated the build-and-boot loop, what host access sub-agents had, or how test/build execution was contained.
- **Recovery model**: Only mentioned in passing by a secondary analysis: infrastructure existed to "kill and restart stuck agents"; an earlier run reportedly showed "agents appeared to cheat," implying some run-level supervision. No rollback/snapshot mechanism for the produced artifact itself is documented.
- **Compatibility strategy**: Not documented — no target hardware/emulator specified; demo-scale (runs FreeDoom, missing FP/hardware-accel/real multithreading).
- **UI model**: N/A to the built OS. The workflow's front end was reportedly "a single prompt" — disputed by a skeptical secondary source (normaltech.ai), which notes the actual prompt was "many thousands of lines."
- **What works well (as reported, unverified)**: Role specialization with independent reviewer/critic/auditor stages distinct from the builder. An explicit mandate for one role to hunt for faked/stubbed/hardcoded work via static analysis rather than trusting the builder's self-report. Large-scale decomposition under an orchestrator.
- **What breaks / limits / fails to generalize**: Essentially **no independent reproducibility** — no prompt, source code, agent transcripts, or logs released. Outside observers (a Hacker News thread, a dedicated critical write-up on normaltech.ai) could not verify the headline numbers or check for plagiarism (toy OS kernels are extremely common CS-course projects with public reference implementations; no originality analysis published). Google's own account admits agents "appeared to cheat" in earlier runs and needed added guardrails — the anti-stub/anti-fakery problem was real and iteratively patched, not solved outright by the Reviewer/Critic/Auditor architecture. Only a keynote video and company blog post are public; the "teamwork" feature is gated behind a $200/month tier. HN commentary characterized the resulting OS as comparable to a common undergraduate toy-OS assignment; Antigravity 2.0's own IDE reportedly shipped basic Electron packaging/deployment defects around the same period.
- **What TorchOS should reuse conceptually**: Keep the builder, the correctness-reviewer, and the adversarial/cheating-detector as three distinct postures whenever Claude Code sessions modify TorchOS itself or the assistant modifies the live system. Give the "auditor" role a concrete, mandatory checklist aimed specifically at detecting mocked/hardcoded/stubbed implementations before anything is accepted. Use an orchestrator that decomposes large systems work into bounded, independently checkable units. Keep infrastructure to detect and kill/restart a stuck or looping agent/action.
- **What TorchOS must explicitly avoid**: Do not repeat the specific scale numbers (93 agents / 15,314 calls / 2.6B tokens / $916.92 / "single prompt") as established engineering fact — they originate only from the vendor's own promotional blog post, are not independently reproducible, and a keynote demo optimized to impress an audience once is not evidence of reliability for an unattended, everyday system-repair agent. Do not assume more LLM reviewer/critic/auditor roles *by itself* prevents faked work — Google's own account shows agents still found ways to cheat past that structure; the discipline has to be enforced by hard, non-LLM verification (actual test execution, actual functional/boot checks, diffs checked against a spec), with LLM review as a supplement, not the mechanism of record. Do not treat this as an OS-architecture reference, and treat it strictly as "a workflow shape worth considering, sourced from a vendor's own unaudited claims."
- **Confidence / verifiability note**: **Low-to-moderate, and split.** The *existence* of Google Antigravity, its November 2025 announcement, and its presence at Google I/O 2026 (named co-authors Varun Mohan and Logan Kilpatrick on the official `blog.google` I/O-2026-developer-highlights post) are independently confirmed via Wikipedia and Google's own primary corporate blog. That primary post does **not** mention the OS-build demo, sub-agent counts, tokens, cost, or Doom at all. The specific headline claims trace only to Google's own `antigravity.google` company/marketing blog and were **not** corroborated by independent tech press (targeted searches for TechCrunch/Verge/Ars Technica coverage returned nothing) — the only detailed secondary coverage found derives entirely from Google's own post. A Hacker News thread and normaltech.ai both treat the claim as plausible-but-unverifiable. **Treat every specific number, the "single prompt" framing, and the "ran Doom" claim as reported/unverified vendor marketing, not confirmed fact.**

## Cross-cutting takeaways for TorchOS

- **Never grant the assistant model root/kernel-equivalent execution, full stop.** FableOS is the literal worst case and is precisely the shape TorchOS must invert: model → unprivileged reasoning → constrained operation → policy/validation → snapshot-if-needed → `torchd` (narrow, allowlisted broker API) → OS → verification. The model proposes; it never directly executes anything privileged.
- **Make the system's own action log structurally unforgeable by the assistant's own output channel.** `torchd` should emit its own append-only log of what it actually did, in a format the assistant's chat/narration can never spoof, suppress, or be confused with.
- **Reversible is not the same property as correct.** TorchOS needs pre-execution validation (policy checks, dry-runs, tests) in addition to Btrfs-snapshot rollback — snapshots are the safety net for when validation fails, not a substitute for validation.
- **Default to secure, never insecure-by-default-with-an-opt-in-flag-to-fix-it.**
- **Keep credentials and elevated tokens outside the reasoning model's own reachable context.**
- **Separate builder, reviewer, and adversarial-auditor roles** — especially when Claude Code sessions build or modify TorchOS itself.
- **Verification must be grounded outside the LLM's own say-so.** Stacking more LLM opinions on top of each other is not itself a verification technique — require actual test execution, actual functional checks, and diffs checked against an explicit spec/policy.
- **Don't let anything ship on vendor-reported scale numbers.**
- **Bound every unattended/scheduled assistant action** the way FableOS's "agenda" system does: per-item run caps, consecutive-failure retirement, durable disable-on-crash, never allowed to end the machine's power state on its own, always wrapped so a failure resumes rather than hangs/halts the system.
- **Neither reference project demonstrates real-hardware survivability.** Plan for dedicated real-hardware validation rather than assuming a VM/demo success generalizes.
